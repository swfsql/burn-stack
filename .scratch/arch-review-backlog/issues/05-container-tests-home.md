# 05: Container tests move to burn-stack

Status: resolved

Blocked by: `../../block-family-choice/issues/03-reset-align-and-checked-packed.md`

Split into the tickets of `../../container-tests-home/issues/` (burn-stack) and

From the test overview of 2026-11-03: burn-stack has 90 lib tests and burn-mamba has
360. The user decided that these tests move. Do it before
`02-residuals-transition.md`, so that a change to `Layers` meets its tests in this
repo.

**Problem:** ADR-0005 says that the tests of a container use `RefBlock`. But 110
tests of burn-mamba are in `src/unified/tests/`. Most of them test a container
mechanism with one family as a stand-in. burn-stack has 35 container tests of its own
(`reference::tests`, `modules::hnet::tests`). So a regression in `Layers` can pass
here and show only when burn-mamba moves its pin.

| File (burn-mamba) | Tests | What it tests |
|---|---:|---|
| `layers.rs` | 20 | The gradient horizon, with Mamba-3 as a stand-in |
| `multi_gate.rs` | 19 | `MultiGateResidual` (some with no block), and `Layers` with Mamba-2 |
| `class.rs` | 33 | Class markers, mostly with Mamba-2. A few run per family |
| `layer.rs` | 5 | `Layer` with an MLP, with Mamba-3 |
| `bidi.rs` | 2 | `BidiLayers`, with Mamba-2 |
| `optim.rs` | 14 | `Segmented` and `MuonPlan`, and the plan of each family |
| `untied.rs`, `capture.rs`, `packed.rs`, `hnet.rs` | 17 | What each family owes to a container |

**Direction:**

- A test of a container mechanism moves to `src/reference/tests.rs`, over `RefBlock`.
  Skip a test that repeats an existing one.
- A test that reads block internals needs another way to reach its state. For
  example, `layers.rs` has 28 lines that set fields of the block for an identity
  prefix. `RefBlock` can grow for this (ADR-0005).
- burn-mamba keeps what a family owes. This is one generic contract suite, run once
  for each family, plus `untied`, `capture`, `packed`, `hnet` and the plan of each
  family. A consumer cannot run such a suite yet: `reference.rs` has no public
  contract function, and `reference/tests.rs` is private. Add the suite under the
  `test-helpers` feature.

**Keep the catch:** A real block can break a contract in a way that `RefBlock` cannot.
So the contract suite in burn-mamba stays, and it must run under a gradient horizon,
class markers and multi-gate residuals.

**Docs:** `../burn-mamba/docs/agents/testing.md:10` presents these tests as a seam of
burn-mamba. Update that row in this work, and name the contract suite there.

**Not blocked by this:** The `block-family-choice` tickets do not need it. `layers.rs`
and `multi_gate.rs` use `LayersBuilder` with family configs, and these do not change.

Split this ticket by repo at triage.

**Terms:** **Block contract** and **Family crate** are in `GLOSSARY.md`.

**The split:**

- burn-stack proves "block contracts ⇒ the containers work". It tests each container
  with `RefBlock`, and each contract function with a private test block that breaks
  that contract.
- Each family crate proves "my blocks ⇒ block contracts". It calls the whole suite on
  every block setting that it ships. No family crate tests a container. burn-mamba is
  not special.
- If a family crate needs a property that no contract states, its coverage drops. The
  fix is a new contract in burn-stack.

**The suite:**

- `src/block_contract.rs`, under `any(test, feature = "test-helpers")`.
- One `pub fn` for each contract, generic over `C: BlockConfig`. It takes the config, the
  `Options` and an fp32 tolerance. The tolerance goes through `dtype_tol`. The check of
  a value that can be large uses `max_rel_diff`.
- A contract checks the bare block when it can. It puts the block in a container only
  when the property needs one.
- A contract that does not apply to a block skips it. The block gives the reason (for
  example, its `reset_align` is `None`). burn-mamba keeps no list of skips.
- burn-stack runs the suite on `RefBlock` with a near-zero tolerance, and deletes its
  own tests that repeat a contract.
- The ticket that adds the suite adds one consequence to ADR-0005: "A family crate tests
  its own blocks with the block contracts, through `test-helpers`. It does not test the
  containers again."

**New homes in burn-stack:**

- The 14 tests that use no block go to the sibling `tests.rs` of their module:
  `src/modules/multi_gate/tests.rs` (6), `src/utils/class/tests.rs` (3) and
  `src/optim/segmented/tests.rs` (5).
- The `RefBlock` tests go to `src/reference/tests/`, one file for each mechanism.

**The sort rule:** each batch ticket asks these questions of each test, in order:

1. Does it test a container (can `RefBlock`, or no block, take the place of the Mamba
   block)? Then it moves to burn-stack, or burn-stack drops it as a repeat.
2. Does every family crate need the same test for its own blocks? Then it becomes a
   block contract, and burn-mamba calls the contract.
3. Does only Mamba need it? Then it stays in burn-mamba.

The first step of each batch ticket writes a list under its `## Comments`. The list has
one line for each test: the rule number and the new home. `grad_horizon_memory_probe` follows rule 1.
It moves to burn-stack over a `RefBlock` that is large enough for the activations to set
the peak memory.

**Batches** (about 2–3k lines of reads each, with the matching burn-stack tests):

- A: `class.rs`
- B: `layers.rs`, `layer.rs`, `bidi.rs`
- C: `multi_gate.rs`, `optim.rs`

**Block settings in burn-mamba:** the suite runs on each setting that a test in

**Coverage:**

- One script, `scripts/coverage.py` in burn-stack, takes the path of a crate. It measures
  line, branch and condition coverage of the `src/` of that crate with its own tests, on
  nightly. Nightly rustc has no MC/DC (`-Zcoverage-options` accepts only `block`,
  `branch` and `condition`). Condition coverage is the nearest to MC/DC.
- The `check.sh` of each repo runs it by default. burn-mamba runs
  `../burn-stack/scripts/coverage.py`.
- A compare mode reports each covered item that a change lost since a base commit, in
  the same way as `compare_reports.py`. There is no stored baseline.
- The gate of this move starts with a record before the first batch. The record holds
  the coverage of `src/` in both repos by both test suites. burn-mamba uses its
  `[patch]` path for this record. After each batch, both suites together must cover
  each line, branch and condition of that record.
- Risk: `cargo llvm-cov` may not report burn-stack, because it is not in the workspace
  of burn-mamba. The coverage ticket checks this. If it cannot report burn-stack, the gate
  of this move is the lists of the batches and the review.
- The user installs `cargo-llvm-cov` and the nightly `llvm-tools-preview` through the
  box build.

**Order:**

2. The contract suite, with its negative tests and the line in ADR-0005.

4. One burn-mamba ticket. It deletes the moved tests and calls the suite on each
